第 2 版改了什么

里程碑顺序倒过来了。 原计划先写 Markdown 解析（M1）、最后做 GUI。实际动手后确认：解析那部分对你没有吸引力，而动力是单人半年项目里最稀缺的资源。所以先做看得见的那一半。

另外修正三处旧判断：GPUI 文档不再稀薄（已有教程和两本社区书）；装 TeX 应为 tectonic 而非 MacTeX；nvim 的 ui.txt 已更名 api-ui-events.txt。

为什么是这个

空缺是真实的，而且已被反复验证

现有的 nvim 内联渲染方案——mdmath.nvim、render-latex.nvim、diagram.nvim、image.nvim—— 全部依赖终端图形协议。这意味着必须用 Kitty / WezTerm / Ghostty，tmux 透传脆弱，SSH 场景经常崩。

而 Neovide（15.2k star，Rust）被请求实现这件事已经很多年： #2117 widget protocol、 #2088 image rendering， 至今空缺。需求被验证过，机制被讨论清楚，没有既得者。

但同一个事实也是警告：一个有多名维护者的成熟项目多年没做成，说明难点不在"把图画出来"， 而在滚动、折叠、分屏、缩放时让图始终待在正确的位置。

第二个差异化点，几乎是免费的

预览和 PDF 导出可以共用同一个 TeX 引擎、同一份 preamble—— 所见即所得不是靠对齐两套渲染器，而是结构上只有一套。 Obsidian 永远做不到：它预览用 MathJax、导出用 Chromium 的 printToPDF。

决策结论理由 / 代价
能力顺序a → b → c → d（第 2 版改）原为 a→c→b→d，理由是 GPUI 文档稀薄、Rust 不牢会卡在编译器上。前者已不成立；后者仍成立，但可以通过 GUI 项目来学，不必通过 parser。动力是更稀缺的资源。
M1 的内部顺序先做"编译并显示"，后做"从 markdown 里找块"M1 本是两半：解析 + 渲染。渲染那半有视觉反馈、且不含 nvim 协议，是更好的起点。解析没取消，只是后移。
渲染范围TikZ 块 + $$ 块级公式两者共用同一条管线，增量成本近零而使用频率高十倍。明确不做 $…$ 行内——难点是基线对齐而非解析。
Markdown 样式全部委托 nvim 插件粗体、斜体、标题高亮不属于你的问题域。
TeX 引擎tectonic，trait 抽象 + 系统 TeX fallback是 Rust crate、自包含、按需下载宏包。已实测：首次运行会下载 LaTeX 基础层并构建 format，之后离线。加宏包时会再来一波。
PDF 导出pandoc 转结构，preamble 你自己拥有不写导出器，但拥有 preamble——一致性成为结构性保证。
wikilink / 索引自己写理由是学习、图谱依赖这张链接表、进程隔离不卡编辑器。不是性能。
Vault 兼容完全兼容 Obsidian-flavored用你真实的 248 篇 vault 当验收集。代价是解析阶段慢一到两周。
架构 A／B／C／D推迟到第 16 周再定这条没变，而且第 2 版更重要了。先做的静态渲染器在四条路里通用；一旦现在动"rusidian 的 GUI"，就等于被迫提前选型。
AI 边界已写入 CLAUDE.md可解释、可 review、可查文档、可诊断报错；不产出你没有逐行理解的实现。每个模块完成后关掉 AI 写设计说明。

最后

三个我不替你解决的风险

一、你还在学 vim 本身。 配置是新建的，还装着 vim-be-good。在尚未定型的工作流之上造工具，风险是你现在不知道半年后想要什么。缓解办法只有一个：这半年高强度用 nvim 写课程笔记，让需求自己浮出来。

二、GPUI 是 pre-1.0，破坏性变更频繁。 版本钉死，升级要挑时间，别在赶里程碑的当口升。

三、最大的风险是我。 上一个 Rust 项目是 AI 写的，结果是"我都不会"。规则已写进 CLAUDE.md，但规则挡不住某个深夜你想让我"就这一次，直接把这个文件写完"。到那时你要自己按住。

自检

每完成一个模块，关掉 AI，用自己的话写一段设计说明提交进 repo。写不出来就说明没真懂——回去重写那个模块，而不是继续往前赶。这是整个计划里唯一无法被绕过的验收标准。
