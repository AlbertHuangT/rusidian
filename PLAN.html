为什么是这个

空缺是真实的，而且已被反复验证

现有的 nvim 内联渲染方案——mdmath.nvim、render-latex.nvim、diagram.nvim、image.nvim—— 全部依赖终端图形协议。这意味着必须用 Kitty / WezTerm / Ghostty，tmux 透传脆弱，SSH 场景经常崩。

而 Neovide（15.2k star，Rust）被请求实现这件事已经很多年： #2117 widget protocol、 #2088 image rendering， 至今空缺。需求被验证过，机制被讨论清楚，没有既得者。

但同一个事实也是警告：一个有多名维护者的成熟项目多年没做成，说明难点不在"把图画出来"， 而在滚动、折叠、分屏、缩放时让图始终待在正确的位置。 这是你真正要解决的问题，请从第一天起就这么理解它。

第二个差异化点，几乎是免费的

预览和 PDF 导出可以共用同一个 TeX 引擎、同一份 preamble—— 所见即所得不是靠对齐两套渲染器，而是结构上只有一套。 Obsidian 永远做不到：它预览用 MathJax、导出用 Chromium 的 printToPDF， 这正是你遇到的导出与预览不一致的根因。

决策结论理由 / 代价
渲染范围TikZ 块 + $$ 块级公式两者共用同一条管线，增量成本近零而使用频率高十倍。明确不做 $…$ 行内——难点是基线对齐而非解析。
Markdown 样式全部委托 nvim 插件粗体、斜体、标题高亮不属于你的问题域。
TeX 引擎tectonic 优先，trait 抽象 + 系统 TeX fallback是 Rust crate、自包含、按需下载宏包，安装说明从「先装 5GB MacTeX」变成「下载即用」。代价：XeTeX 基座、shell-escape 受限。第一周必须实测三个宏包。
PDF 导出pandoc 转结构，preamble 你自己拥有不写导出器，但拥有 preamble——一致性成为结构性保证。自己写 Markdown→PDF 是几百小时且零差异化。
wikilink / 索引自己写理由是学习、图谱依赖这张链接表、进程隔离不卡编辑器。不是性能——248 篇笔记下 LuaJIT 和 Rust 都是毫秒级。
Vault 兼容完全兼容 Obsidian-flavored用你真实的 248 篇 vault 当验收集：有脏数据的真语料比造出来的测试用例值钱。代价是 M1／M2 慢一到两周。
架构 A／B／C／D推迟到第 16 周再定引擎与 Lua 协议插件在四条路里通用且不含 GUI 代码。等你有了真实 Rust 能力和对 RPC 的实感再选，才是有信息的决定。
能力顺序a → c → b → d跳过 a 直接上 GPUI 是这个计划最常见的死法：文档稀薄，报错全是生命周期和 trait bound，基础不牢的人会卡在编译器上失去信心。
AI 边界已写入 CLAUDE.md可解释、可 review、可查文档、可诊断报错；不产出你没有逐行理解的实现。每个模块完成后关掉 AI 用自己的话写设计说明。

需要提前接受的心理事实

M2 之前，你自己写的 wikilink 索引不会比 obsidian.nvim 好用。这段时间你日常照用 obsidian.nvim，自己那个只在测试里跑。不提前认下这件事，第 10 周你会觉得自己在做无用功。

最后

三个我不替你解决的风险

一、你还在学 vim 本身。 配置是两天前建的。在尚未定型的工作流之上造工具，风险是你现在不知道半年后想要什么。缓解办法只有一个：这半年高强度用 nvim 写你的课程笔记，让需求自己浮出来。

二、公开项目的采纳不取决于代码质量。 取决于安装门槛、README 的第一屏、和那个 demo GIF。这是 M3 的真正内容，不是附赠品。

三、最大的风险是我。 你上一个 Rust 项目是 AI 写的，结果是"我都不会"。规则已经写进 CLAUDE.md，但规则挡不住第 14 周某个深夜你想让我"就这一次，直接把这个文件写完"。到那时你要自己按住。

自检

每完成一个模块，关掉 AI，用自己的话写一段设计说明提交进 repo。写不出来就说明没真懂——那就回去重写那个模块，而不是继续往前赶。这是整个计划里唯一一条无法被绕过的验收标准。
